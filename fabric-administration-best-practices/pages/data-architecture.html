5. Data Architecture & Naming Conventions

Lakehouse vs Warehouse, medallion architecture, data formats, and the complete DGE naming standard.

Choosing: Lakehouse vs. Warehouse

Fabric offers both a Lakehouse (Spark-based, Delta Lake) and a Warehouse (T-SQL, fully managed). They can coexist in the same architecture.

Criteria Lakehouse Warehouse
Engine Apache Spark + SQL analytics endpoint (read-only SQL) Full T-SQL engine (read + write)
Best for Data engineering, large-scale transformations, data science, semi-structured data Business logic in stored procedures, complex SQL joins, familiar SQL Server patterns
Write method Spark (PySpark, Scala), Dataflows, Pipelines T-SQL INSERT/UPDATE/DELETE, stored procedures, COPY INTO
Storage format Delta Parquet (open format in OneLake) Delta Parquet (open format in OneLake)
Schema enforcement Schema-on-read (flexible), Delta schema enforcement optional Schema-on-write (strict), enforced constraints
Security model OneLake security roles + SQL grants on analytics endpoint Full T-SQL security (GRANT/DENY/REVOKE, RLS, CLS)
CI/CD Git-integrated (metadata only; data not stored in Git) Recommend separate workspace, not Git-integrated; deploy via dacpac/SQLPackage
ℹ Common Pattern
Use Lakehouse for Bronze and Silver layers (data engineering with Spark), and either a Lakehouse or Warehouse for Gold depending on your team's SQL expertise. If using a Warehouse in Gold, create shortcuts in a gold Lakehouse to expose Warehouse tables for OneLake/Spark access.

Data Formats: Delta Parquet & Iceberg

All data in OneLake is stored in open formats — this prevents vendor lock-in and ensures future interoperability with other government platforms.

Delta Lake (Default)

  • Default table format for all Fabric Lakehouses and Warehouses
  • Supports ACID transactions, time travel, schema evolution
  • Optimised for both batch and streaming workloads
  • Readable by any tool that supports Parquet + Delta protocol

Apache Iceberg

  • Fabric supports Iceberg tables via metadata virtualisation
  • Iceberg tables can be read as Delta tables across Fabric, and Delta tables can be accessed by Iceberg-compatible services (e.g., Snowflake)
  • Useful when data needs to be shared with non-Microsoft platforms
✓ Relevance for Abu Dhabi Government
Open formats (Delta/Iceberg) ensure your data is not locked into a proprietary format. If policies change or a new platform is adopted, your data remains accessible without costly migration. This aligns with government data sovereignty and interoperability requirements.

Medallion Architecture (Bronze / Silver / Gold)

The medallion architecture organises data into layers of increasing quality and business readiness:

Layer Purpose Data Format Who Accesses
Bronze Raw ingestion — exact copy of source data. Immutable historical record. Supports re-processing if logic changes. Delta format recommended (even for raw data) — enables time travel, schema enforcement, and efficient queries. Raw files (JSON, CSV, Parquet) land in /Files/bronze/ before being loaded into Delta tables. Data engineers only
Silver Cleansed, conformed, deduplicated. Standard data types, null handling, business keys applied. This is the "enterprise-ready" layer. Delta tables. Optimised with Z-ORDER on common filter columns. Data engineers, data scientists
Gold Business-ready, aggregated, modelled (star schema: facts + dimensions). Optimised for reporting and analytics consumption. Delta tables (Lakehouse) or Warehouse tables. Semantic models built on top. BI developers, business users (via semantic models/reports)
⚡ Should Bronze Be Delta?

Yes — store Bronze as Delta tables. While raw files initially land in /Files/bronze/ (landing zone), they should be immediately loaded into Delta tables in /Tables/. This provides:

  • Time travel — reprocess from any point in history
  • Schema enforcement — catch source schema changes early
  • Efficient queries — Spark/SQL can query Bronze directly for debugging
  • VACUUM support — manage storage growth over time

Keep the raw files in /Files/ as an archive/landing zone, but your primary Bronze tables should be Delta.

DGE Naming Conventions Standard

ℹ Global Rules
Use: lowercase, snake_case, descriptive names, standard prefixes
Avoid: spaces, special characters, Final, Final_v2, New, Test123, MyReport
Environments: dev, test, prod

Convention Design Rationale

All item names follow one of three structural patterns, chosen based on what information you need at a glance:

Item Category Pattern Structure Why
Storage items
(Lakehouse, Warehouse, KQL DB, Eventhouse)		 prefix_<domain>_<layer> You need to know: what data domain and what stage in the pipeline. These are "locations" in your architecture.
Processing items
(Pipeline, Notebook, Dataflow, Eventstream)		 prefix_<action>_<target> You need to know: what it does and what it operates on. These are "verbs" that move/transform data.
Consumption items
(Semantic Model, Report, App, Data Product, Data Agent)		 prefix_<domain>_<descriptor> You need to know: which business area and what business concept it serves. These are "outputs" for users.

Processing Items — prefix_<action>_<target>

All workload/processing items follow an action-oriented pattern. The <target> describes what the item operates on, and its format depends on the action:

Action Target describes Example
ingestThe entity being loaded (source data)pl_ingest_hotel_occupancy
transformThe destination: <domain>_<layer>nb_transform_tourism_silver
cleanThe destination: <domain>_<layer>nb_clean_events_silver
validateWhat is being checkedpl_validate_tourism_gold
publishWhat is being publishedpl_publish_executive_kpis
refreshWhat is being refreshedpl_refresh_tourism_gold
archiveWhat is being archivedpl_archive_events_bronze
masterThe scope of orchestrationpl_master_tourism_daily
streamThe data being streamedes_stream_event_attendance
⚡ Why target format varies by action

This is intentional, not inconsistent. An ingest pipeline naturally names its source entity ("I ingest hotel_occupancy"), while a transform notebook names its destination ("I transform data into tourism_silver"). Forcing a rigid structure for all actions would make names less readable.

The rule: target = whatever makes the item's purpose obvious at a glance.

ℹ Why Shortcuts differ
Shortcuts use sc_<source>_<target> instead of sc_<domain>_<descriptor> because shortcuts are references to external or cross-workspace data. Knowing the source system (adls, s3, onelake) is more useful than the domain when debugging connectivity or access issues.

Table & Column Naming

Tables use a type prefix + entity pattern. The prefix tells you the table's role in the data model.

✓ No layer prefixes on tables

Tables in Bronze/Silver lakehouses do NOT need br_ or sl_ prefixes — the layer is already encoded in the lakehouse name (lh_tourism_bronze). Adding a layer prefix to the table is redundant and creates unnecessary refactoring risk if tables are ever moved.

Use plain entity names in Bronze and Silver. Reserve prefixes for the Gold layer where they describe the table's role in the star schema.

Layer Table Naming Rationale
Bronze <entity> — no prefix Layer is known from lh_*_bronze. Tables mirror source entity names.
Silver <entity> — no prefix Layer is known from lh_*_silver. Same entity, cleansed.
Gold fact_, dim_, ref_, agg_, vw_ Gold tables serve a star schema — the prefix describes the table's role (not its layer).
Any layer stg_, audit_, ctl_ Utility tables that exist for operational purposes, not consumption.
