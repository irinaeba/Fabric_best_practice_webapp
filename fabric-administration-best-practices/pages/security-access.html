4. Security & Access Control

Network security, workspace roles, item permissions, OneLake security, service principals, and data gateways.

Network Security

For Abu Dhabi government entities, network controls are a critical layer of defence:

Feature What It Does When to Use
Microsoft Entra Conditional Access Restrict access based on IP ranges, MFA, device compliance, location Always — enforce MFA, block access from non-compliant devices, restrict to UAE-based IPs
Private Links Restrict Fabric tenant access to traffic from an Azure VNet only; block all public access High-security environments where all access must traverse a private network
Managed Virtual Networks Dedicated VNet for Fabric Spark workloads; compute clusters isolated in a private network When Spark notebooks/jobs need to connect to private data sources
Managed Private Endpoints Private connections from Fabric to data sources (Azure SQL, ADLS) without public exposure Connecting to Azure PaaS services that have public access disabled
⚠ Government Recommendation
At minimum, enable Conditional Access with MFA enforcement and IP-based restrictions. For sensitive workloads, combine with Private Links to eliminate public internet access to Fabric entirely.

Workspace Roles

Fabric workspaces have four roles: Admin, Member, Contributor, Viewer. Always use security groups rather than individual user assignments.

Item-Level Permissions & Sharing

⚠ Critical Misconception to Understand

A user with Viewer access on a workspace can see ALL items in that workspace.

However, if you share a specific item (e.g., a report or semantic model) directly with a user who has NO workspace role, that user can ONLY access that specific shared item — they cannot see or access any other content in the workspace.

This is a very common misconception. Use item-level sharing when you need to give someone access to a single report without exposing the entire workspace.

When to Use Item-Level Sharing

  • Business users who need a specific report — Share the report directly; don't add them to the workspace
  • Cross-department data access — Share a semantic model with Build permission so another team can create reports from it
  • External stakeholders (if B2B is enabled) — Share specific items only

Data-Level Security

Security Type What It Controls Where It Applies
Row-Level Security (RLS) Which rows a user can see Semantic models, SQL analytics endpoint, Warehouse
Column-Level Security (CLS) Which columns a user can see SQL analytics endpoint, Warehouse
Object-Level Security (OLS) Which tables/objects are visible Semantic models

OneLake Security Roles

OneLake security roles provide granular folder and table-level access control within a Lakehouse, independent of workspace roles.

What Are OneLake Security Roles?

  • They define permissions on specific folders and tables within a Lakehouse's OneLake storage
  • You can grant or deny access to individual folders (e.g., /Tables/fact_hotel_occupancy) or file paths
  • They are enforced across all analytics engines — SQL, Spark, Power BI all respect the same rules
  • A user may have workspace Contributor role but still be restricted to only certain tables via OneLake security roles

When to Use

  • When different teams need access to the same Lakehouse but different tables
  • When you need to restrict Spark/API-level access (workspace Viewer blocks Spark access entirely, but OneLake roles allow fine-grained control for Contributors)
  • For data science scenarios where data scientists need Spark access to specific tables but not the entire lakehouse

Service Principals & Managed Identities

Identity Type What It Is When to Use Common Scenarios
Service Principal
(App Registration)		 A non-human identity (client ID + secret/certificate) registered in Entra ID Automation that runs outside Fabric — CI/CD pipelines, external scripts, DevOps agents
  • Deploying artefacts via Fabric REST APIs
  • Running deployment pipelines from Azure DevOps
  • Automated workspace provisioning
  • Programmatic metadata scanning
Managed Identity
(System or User-assigned)		 An Azure-managed identity tied to a resource — no secrets to manage Fabric connecting to other Azure services securely
  • Fabric Pipelines accessing Azure Key Vault
  • Connecting to ADLS Gen2 with firewall (Trusted Workspace Access)
  • Connecting to Azure SQL Database
Workspace Identity A Fabric-managed identity specific to a workspace (requires F SKU) When a workspace needs to access firewall-protected Azure resources
  • Trusted workspace access to ADLS Gen2
  • Secure outbound connections without gateways
⚡ Best Practice
  • Use Service Principals for CI/CD automation — never use personal accounts for deployments
  • Use Managed Identities whenever connecting to Azure services — they eliminate secret management
  • Store Service Principal secrets in Azure Key Vault, never in code or pipeline variables
  • Enable "Allow service principals to use Fabric APIs" tenant setting for a specific security group only

Data Gateways

Gateways bridge Fabric to data sources that are not publicly accessible or not in Azure.

Gateway Type When to Use How It Works
On-Premises Data Gateway Connecting to data sources inside your corporate network or behind a firewall (on-premises SQL Server, file shares, SAP, Oracle, etc.) Installed on a VM/server within your network. Acts as a bridge — Fabric sends requests to the gateway, which fetches data locally and returns it.
VNet Data Gateway Connecting to Azure PaaS services inside a VNet (Azure SQL, Azure Synapse, Cosmos DB) without an on-premises gateway installation Microsoft-managed gateway deployed into your VNet. No infrastructure to manage.

VNet Gateway: Supported Data Sources

VNet data gateways support connections to:

  • Azure SQL Database / Azure SQL Managed Instance
  • Azure Synapse Analytics
  • Azure Data Lake Storage Gen2 (within a VNet)
  • Azure Cosmos DB
  • Azure Database for PostgreSQL
  • Azure Databricks
ℹ When VNet Gateway is NOT supported
Use an On-Premises Data Gateway for:
  • On-premises SQL Server, Oracle, SAP
  • File shares and SFTP
  • Non-Azure cloud databases (AWS RDS, GCP Cloud SQL)
  • Any source not available as Azure PaaS

Key Vault Support for Connections

Azure Key Vault can be used to store credentials for data connections, but support varies:

Connection Type Key Vault Supported Notes
Data Pipeline connections (Data Factory) ✓ Yes Use Key Vault linked service for secrets in pipeline activities
Notebook / Spark connections ✓ Yes Access Key Vault via mssparkutils.credentials.getSecret()
Dataflow Gen2 connections ✗ Limited Uses built-in connection manager; Key Vault not directly supported
Semantic Model / Report connections ✗ No Use gateway-managed credentials or OAuth/SSO
On-Premises Gateway connections ✗ No Credentials stored encrypted in gateway configuration
Lakehouse / Warehouse (OneLake) N/A Uses Entra ID authentication — no stored credentials needed
⚡ Recommendation
For government environments: use Azure Key Vault wherever supported (Pipelines, Notebooks). For Dataflows and Semantic Models, rely on OAuth/SSO or Managed Identity authentication to avoid storing credentials. For on-premises gateways, ensure the gateway service account follows your organisation's password rotation policy.
