6. CI/CD & Lifecycle Management

How workspace design impacts CI/CD, deployment options, Git integration, and the recommended workflow.

ℹ Key Reference
This section is informed by Thoughts on Workspace Design — Part 3: Optimising for CI/CD by Nicholas Hurt (Microsoft Customer Success Unit), and the official Fabric CI/CD documentation.

Why Workspace Design Impacts CI/CD

The structure of your workspaces directly determines how complex your deployment process will be.

Monolithic Workspace Modular Workspace
All items (pipelines, notebooks, lakehouses, warehouse, reports) in one workspace Items separated by function (ingestion, transformation, serving, reporting)
Branch-out takes longer (more items to sync) Branch-out is fast (fewer items per workspace)
Complex dependency chain — pipelines reference lakehouses, notebooks reference warehouses Minimal cross-references within each workspace
Higher risk of deployment failures (dependencies out of order) Deployments affect fewer items, less chance of conflicts
Developers may accidentally overwrite each other's references Developers work on isolated, purpose-specific workspaces
✓ Key Takeaway
A modular workspace design dramatically simplifies CI/CD. Fewer items = faster branch-out, fewer references to reconfigure, fewer deployment conflicts. This is the design used by Microsoft's own internal teams building data solutions in Fabric.

CI/CD Options in Fabric

Fabric supports three main approaches to deploying content across environments:

Option How It Works Best For Complexity
Option 1
Git-based deployments		 Each environment (Dev, Test, Prod) is a workspace connected to a different Git branch. Merging a PR to the target branch auto-syncs the workspace. Simple setups with few items. Good for reports and semantic models. Low–Medium
Option 2
Git + Build environment		 Dev workspace connected to Git. A CI/CD pipeline (Azure DevOps / GitHub Actions) reads from Git and deploys to higher environments using Fabric APIs or the fabric-cicd Python library. Recommended for most scenarios. Full control, parameterisation, automated testing. Medium
Option 3
Fabric Deployment Pipelines		 Built-in Fabric feature. Deploy content between workspaces (Dev → Test → Prod) with a visual UI. Supports deployment rules for parameter changes. Teams without DevOps expertise. Quick setup. Good for BI content. Low

Recommended Approach for DGE

For Data Engineering Items (Pipelines, Notebooks, Lakehouses)

Use Option 2: Git + Build Environment with the open-source fabric-cicd Python library.

  1. Dev workspace connected to Git (Azure DevOps — use a UAE-hosted organisation)
  2. Developers branch out to private workspaces for feature work
  3. PR to main branch triggers a CI/CD pipeline
  4. Pipeline deploys to Prod workspace via Fabric APIs

For Warehouse (T-SQL objects)

Keep the Warehouse in a separate workspace that is NOT Git-integrated. Instead:

  1. Version-control the dacpac / SQL project in Git
  2. Deploy using SQLPackage in a release pipeline
  3. This gives full control over schema migrations without Git sync issues

For BI Content (Semantic Models, Reports)

Option 3: Fabric Deployment Pipelines is suitable for teams without heavy DevOps skills. Alternatively, Option 2 with fabric-cicd for full automation.

Source Control Platform

The choice of Git platform depends on your organisation's data classification. Not all workloads belong in Azure DevOps Services (cloud-hosted).

Data Classification Recommended Platform
Public / Internal Azure DevOps Services (cloud-hosted)
Confidential Government Data Assess with DGE governance team
Sovereign / Restricted Data Azure DevOps Server (self-hosted in UAE) or approved sovereign Git platform
⚠ Abu Dhabi Government RFPs
The safest default position for Abu Dhabi government entities is Sovereign / Restricted. Assume this classification unless the governance team explicitly approves a lower tier. This means source control infrastructure should reside in-country (UAE) or on an approved sovereign platform.

Git Integration Setup

Prerequisites

  • Git platform selected based on data classification (see above)
  • If using Azure DevOps Services — organisation hosted in UAE region
  • If sovereign — Azure DevOps Server deployed on UAE infrastructure
  • Git repository created in Azure Repos
  • Workspace Admin role (only Admins can connect workspaces to Git)
  • Fabric tenant setting: "Users can synchronize workspace items with their Git repositories" → Enabled

Branching Strategy

main ← Connected to Dev workspace. Always deployable. │ ├── feature/add-hotel-pipeline ← Developer's private workspace ├── feature/update-events-model ← Another developer └── bugfix/fix-refresh-schedule ← Hot-fix branch
  • main — Source of truth. Connected to the Dev workspace. Always in a deployable state.
  • feature/* — Short-lived branches for new work. Developer branches out to their own workspace.
  • bugfix/* — Emergency fixes. Same process but expedited review.
  • No direct commits to main — all changes go through Pull Requests with review.

Variable Libraries

Variable libraries solve the problem of environment-specific configurations — values that differ between Dev and Prod (connection strings, lakehouse IDs, etc.).

What They Replace

  • Hardcoded lakehouse/warehouse references in pipelines and notebooks
  • Environment-specific connection strings
  • Deployment rules in deployment pipelines

How They Work

  • Define variables once in the workspace's Variable Library
  • Reference variables in pipeline expressions, notebook parameters, queries
  • Each workspace (Dev, Prod) has its own Variable Library with environment-appropriate values
  • When items are deployed, the variable references stay the same — only the values differ per environment

Developer Workflow (Step-by-Step)

1. Start a New Feature

1. Create a new branch from main: feature/add-museum-visits-pipeline
2. Branch out to a new workspace (Fabric UI or automation script)
   → This creates: "DGE-Tourism Insights [Dev] - feature/add-museum-visits-pipeline"
3. Workspace syncs items from the feature branch

2. Develop & Test

4. Build your pipeline / notebook / report in the private workspace
5. Test with dev data
6. Commit changes to the feature branch (Source Control pane in Fabric)

3. Submit for Review

7. Create a Pull Request from feature branch → main
8. Peer review: code review + functional validation
9. Resolve any merge conflicts
10. PR approved and merged → main branch updated

4. Deploy to Production

11. CI/CD pipeline triggers (Azure DevOps)
12. Pipeline reads from main branch
13. Deploys to Prod workspace via Fabric APIs / fabric-cicd library
14. Variable Library in Prod resolves environment-specific values
15. Post-deployment validation runs

5. Clean Up

16. Delete the feature branch
17. Developer reuses their workspace for the next feature
    (switch branch connection to a new feature branch)

Special Case: Data Warehouse CI/CD

⚡ Warehouse ≠ Git Integrated

The fabric-cicd library does not currently support publishing Data Warehouse items. The recommended approach:

  1. Keep the Warehouse in a separate workspace (not Git-connected)
  2. Use a SQL Database Project (.sqlproj) in your Git repo for version control
  3. Deploy schema changes via SQLPackage (dacpac) in your Azure DevOps release pipeline
  4. This gives you full migration control, rollback capability, and schema diff

Reference: Guide to Database Projects for Fabric Data Warehouses
