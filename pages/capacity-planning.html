1. Capacity & Licensing Planning

Estimate the right SKU, plan your environments, and manage costs effectively.

Estimating the Right SKU Capacity

Choosing the correct Fabric capacity SKU (F2, F4, F8, F16, F32, F64, F128, etc.) depends on the number of concurrent users, workload types, data volume, and refresh frequency.

Fabric Capacity Estimator

Microsoft provides the Fabric Capacity Metrics app to help you understand current consumption and right-size your capacity.

ℹ Enhanced Estimator — Coming Soon
A more detailed capacity estimation tool tailored for Abu Dhabi government workloads is currently in development and will be added to this guide once available. It will factor in typical government data volumes, refresh patterns, and concurrent user loads.

Key Factors for SKU Sizing

  • Number of workloads: Data engineering (Spark), data warehousing (SQL), real-time analytics, Power BI reports
  • Concurrency: How many users/processes run simultaneously during peak hours
  • Data volume: Total data size and daily incremental loads
  • Refresh frequency: How often semantic models and pipelines refresh
  • Burst vs. sustained: Fabric smooths compute usage over time — short bursts are handled well, sustained heavy loads need larger SKUs
⚡ Start Small, Scale Up
It is recommended to start with a smaller SKU and monitor consumption using the Capacity Metrics app. You can scale up at any time without downtime.

Environment Strategy (Dev / Prod)

Microsoft recommends a full DTAP approach (Development, Test, Acceptance, Production). However, at minimum, you need two environments:

Environment Purpose Who Uses It Capacity
Development (Dev) Build, experiment, iterate on data pipelines, notebooks, reports. Break things safely. Data engineers, BI developers, data scientists Smaller SKU (e.g., F4–F16). Can be shared across dev teams.
Production (Prod) Serves business users. Stable, tested, governed. Only deployed artefacts land here. Business users (consumers), automated pipelines, scheduled refreshes Sized for production workloads and concurrency (e.g., F32–F128).

Why Separate Capacities?

  • Workload isolation: A developer running a heavy Spark job should never affect production report performance
  • Billing separation: Each capacity can be on a different Azure subscription for clear cost attribution
  • Security boundary: Different access controls per environment
  • Governance: Only approved artefacts are promoted to production via CI/CD
ℹ Optional: Test Environment
If resources allow, add a Test/UAT environment between Dev and Prod. This is where business users validate changes before production deployment. It should mirror production data volumes and capacity sizing as closely as possible.

Cost Management & Chargeback

Understanding Fabric billing is critical for government entities that need to allocate costs across departments.

How Fabric Billing Works

  • Fabric uses Capacity Units (CUs) as the universal compute measure
  • All workloads (Spark, SQL, Power BI, Pipelines) consume CUs from the same capacity pool
  • CU consumption is smoothed over time — short bursts don't immediately throttle, but sustained overuse does
  • Storage (OneLake) is billed separately at a per-GB rate

Chargeback Strategies

Strategy How It Works Best For
Separate capacities per department Each department gets its own F-SKU capacity, billed to their Azure subscription Large entities with distinct budgets per department
Shared capacity + Metrics app Single capacity shared across teams; use Capacity Metrics app to report usage per workspace Smaller entities or initial rollout phases
Tags & Azure Cost Management Tag capacities with department/project metadata; use Azure Cost Management for reporting Finance teams needing granular cost visibility
