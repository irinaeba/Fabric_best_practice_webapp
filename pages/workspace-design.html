3. Workspace Design & Organisation

How to structure workspaces for billing isolation, workload separation, access management, and CI/CD efficiency.

ℹ Key Reference
This section is informed by Thoughts on Workspace Design in Microsoft Fabric — Part 1 by Nicholas Hurt (Microsoft Customer Success Unit). The patterns described here are field-tested with customers transitioning to Fabric.

Why Workspace Design Matters

In Fabric, workspaces are the primary unit of organisation. They determine:

  • Billing isolation — workspaces are assigned to capacities, which map to Azure subscriptions
  • Workload isolation — separating heavy Spark jobs from production reports prevents "noisy neighbours"
  • Access control — workspace roles are the first layer of security
  • CI/CD complexity — monolithic workspaces with many item types dramatically complicate deployments (see Section 6)
⚡ Key Insight
There is currently no way to apportion a single capacity to different workloads or teams. The recommendation is to carve up workloads into workspaces that run on separate capacities, sized according to the workload.

Recommended Pattern: Core Data Provider & Managed Self-Service BI

This pattern addresses three common requirements for government entities:

  1. Billing & workload isolation between data engineering and reporting
  2. Granular data access management using SQL permissions and OneLake security roles
  3. Managed self-service BI where a central team curates data and domain teams build reports

High-Level Architecture

── Data Engineering Capacity (F-SKU) ────────────────── │ ├── DGE-Tourism Insights [Dev] │ ├── lh_tourism_bronze │ ├── lh_tourism_silver │ ├── lh_tourism_gold │ ├── pl_ingest_hotel_occupancy │ └── nb_transform_tourism_silver │ ├── DGE-Events Analytics [Dev] │ ├── lh_events_bronze │ ├── lh_events_silver │ └── ... │ ── Reporting Capacity (F-SKU) ────────────────────────── │ ├── DGE-Reporting Hub ← Central, owned by data team │ ├── lh_transit_tourism ← Shortcuts to gold tables │ ├── sm_tourism_performance ← Semantic model │ └── rpt_tourism_executive_dashboard │ ├── DGE-Tourism Reports ← Domain-specific (optional) │ ├── sm_tourism_operations │ └── rpt_tourism_operations │ └── DGE-Events Reports ← Domain-specific (optional) └── ...

1. Billing & Workload Isolation

At least two Fabric capacities are required:

Capacity Workspaces Assigned Purpose
Data Engineering Capacity Bronze, Silver, Gold workspaces (all environments) Spark jobs, pipeline execution, data transformation
Reporting Capacity Reporting hub, domain report workspaces Semantic model refresh, Power BI report rendering, user queries

Each capacity can be associated with a different Azure subscription for separate invoicing. This ensures business-critical reporting is not affected by demanding data engineering jobs and vice versa.

ℹ OneLake Shortcuts & Billing
When the reporting workspace accesses data from the data engineering workspace via OneLake shortcuts, the transaction usage counts against the calling capacity (reporting). The data engineering capacity only pays for storage costs — not for consumption of that data from another capacity.

2. Data Access Management

To provide granular access to specific tables for semantic model development:

  1. Create a "transit" lakehouse in the Reporting Hub workspace
  2. Create shortcuts in the transit lakehouse pointing to required tables in the gold lakehouse
  3. The transit lakehouse owner should be a member of the data team who has access to gold tables (shortcuts use delegated mode via the lakehouse owner)
  4. Share the transit lakehouse to report builders with Read-only permissions (no options selected in the share dialog)
  5. Grant SQL SELECT privileges on specific tables to control what each user/group can access
⚡ Important: RLS & Direct Lake
If you implement Row-Level Security (RLS) or Object-Level Security (OLS) in the SQL endpoint, Direct Lake queries will fall back to DirectQuery. As an alternative, implement RLS in the semantic model itself to maintain Direct Lake performance.

3. Managed Self-Service BI

In this model:

  • The central data team develops and maintains semantic models in the Reporting Hub
  • Models are endorsed (Certified) and made discoverable via the OneLake catalog
  • Domain report creators are granted Build permissions on the semantic model to create their own reports
  • For "customizable" self-service, share with Build + Modify permissions — this allows adding measures/relationships but not new tables

Reporting Workspace: Single vs. Split

The reporting workspace(s) can be structured in different ways depending on the organisation's size and access requirements:

Approach When to Use Pros Cons
Single Reporting Hub Small–medium entity, few domains, same team manages all reports Simple to manage, single point of governance Can become crowded; broad access needed
Split by Domain/Department Large entity, multiple departments with distinct data ownership and access Clear ownership per domain, granular access, independent governance More workspaces to manage; cross-domain reporting needs planning
Hub + Spoke Enterprise-wide semantic models + department-specific reports Central team controls quality; domains self-serve from certified models Requires clear endorsement and sharing process

Recommendation for DGE

For Abu Dhabi government entities with multiple departments (Tourism, Culture, Events, Heritage, etc.), a Hub + Spoke approach is recommended:

  • Hub: DGE-Reporting Hub — Central transit lakehouses, enterprise semantic models, executive dashboards
  • Spokes: DGE-Tourism Reports, DGE-Events Reports, etc. — Department-specific models and reports

Workspace Separation by Function

For optimal CI/CD and workload isolation, separate workspaces by function rather than bundling everything together:

Workspace Category Contains Owner
Ingestion / Bronze Pipelines, dataflows, bronze lakehouses Data engineering team
Transformation / Silver Notebooks, silver lakehouses Data engineering team
Serving / Gold Gold lakehouse, warehouse, stored procedures Data engineering / database team
Reporting Hub Transit lakehouses (shortcuts), semantic models, enterprise reports Data/BI team (central)
Domain Reports Department-specific semantic models and reports Domain BI developers
✓ Why Granular Workspaces?
  • Feature development and deployment affects fewer items
  • Fewer references to reconfigure during CI/CD
  • Less chance of complex dependencies causing deployment issues
  • Workspace security can be applied at a more granular level
  • Teams can work independently without blocking each other

For detailed CI/CD implications, see Section 6: CI/CD & Lifecycle.

Isolated Developer Workspaces

For development, each developer gets their own private workspace branched from the main development workspace:

  • Use the "Branch out to new workspace" feature in Fabric UI, or automate via the fabric-toolbox accelerator
  • Developer works in isolation — no risk of overwriting other team members' work
  • When ready, submit a Pull Request back to the main branch
  • After merge, the developer workspace can be reused by switching to a new branch
ℹ Workspace Naming for Environments
Follow the DGE naming convention: 
DGE-Tourism Insights [Dev]     ← Development
DGE-Tourism Insights [Test]    ← Test/UAT (optional)
DGE-Tourism Insights           ← Production (no suffix)

Fabric Domains

Use Fabric Domains to logically group workspaces by business area. This enables:

  • Filtering content in the OneLake catalog by domain
  • Delegating governance settings to domain admins
  • Clear ownership boundaries

Recommended Domain Structure

DGE ├── Tourism ├── Culture ├── Events ├── Heritage ├── Shared Reference Data └── Strategy & Performance

Map each domain to its respective workspaces. A domain admin (department data lead) manages governance within their domain.
